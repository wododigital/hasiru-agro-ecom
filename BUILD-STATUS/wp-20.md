## Assumptions (A20-n, 2026-10-20)
- A20-1: `dependsOn: ['core', 'orders']`, not `checkout`: payments never calls checkout (checkout calls payments). The orders transition API is reached through `configurePayments({ orders: PaymentsOrdersPort })` bound at boot (the `configureX` pattern of A04-1), because orders is built in parallel and modules never import each other's internals.
- A20-2: `payments_attempt.provider` is the gateway holding the money (`phonepe | mock | bank_transfer`) and a new `method` column (`online | cod_partial | bank_transfer`) records the buyer's choice. The plan's `cod_partial` provider value would have hidden which gateway to ask for the status of the advance. `mock` attempts always talk to the mock, even after the mode changes.
- A20-3: extra columns on `payments_attempt`: `method`, `applied_at`, `anomaly`, `error`, `next_poll_at`, `poll_count`, `swept_at`, `is_test`; on `payments_refund`: `provider_refund_id`, `actor_id`, `next_poll_at`, `updated_at`; on `payments_webhook_event`: none beyond the plan (`event` nullable for rejected calls).
- A20-4: a captured payment is always recorded as `completed` (truth from the gateway). Whether it counts for the order is `applied_at`; a capture the order cannot take keeps `applied_at = null`, gets `anomaly`, a `payments_refund` row in the new state `task`, and a critical alert (rule keys `payments.late_completed`, `payments.amount_mismatch`). "No state flip" in the row means the order.
- A20-5: one open attempt per order. A second start with the same method returns the open attempt; another method while one is open is refused (`attempt_open`). A retry after a failure gets the next attempt number but keeps the first attempt's `expires_at` (needs 5 min left, the gateway minimum), so stock holds and payment attempts share one clock (A27).
- A20-6: the sweep closes an order (orders hook) only when none of its attempts is pending or applied and the window is over; reason `failed` if the latest attempt failed, else `expired`. An attempt past its window gets one last status check; with no gateway answer it is expired 10 min after the window anyway.
- A20-7: poll cadence is per attempt (`next_poll_at`: first at 20 s, then 20/30/60 s by age) on a one-minute cron, so effective checks are at most once a minute; the return page and webhook are the fast paths. A 429 stops the run and pushes the remaining items back 30 s doubling to 5 min.
- A20-8: webhook dedupe key is `<event>:<merchant order or refund id>:<state>` (the gateway sends no event id). Rejected calls are stored without payload under a random key (for the 3-in-10-min alert) and pruned after 7 days by the sweep.
- A20-9: webhook credentials in mock mode default to a pair derived from `INTERNAL_SECRET`; in sandbox and live with no stored pair every webhook is refused (fail closed) and the poll reconciles.
- A20-10: `CreatePaymentInput.attemptId` (contract) carries the merchant order id `<number>-<attempt>`; the contract comment says it is used as the gateway's merchant order id. The contract's `partial_advance` kind is unused: partial advance is a method that charges the advance through the online gateway.
- A20-11: pay at pickup has no attempt: `paymentOptions` lists it (pickup only, per settings) and checkout/orders handle the unpaid confirmed order. Bank transfer is an offline attempt with its own hold (`bankTransferHours`, default 48 h); staff mark it received with the amount, which is checked like a gateway capture.
- A20-12: the return URL is `/pay/return?a=<attempt uuid>`; the page shows paid / pending (meta refresh 5 s, no JS) / failed (retry link to `/checkout/<orderId>/pay`, overridable with the port's `payLink`) / review, and checks the gateway at most 30 times per attempt per 10 min.
- A20-13: refunds by staff (`refund()`) settle the order through `markRefunded` only for applied payments; refund tasks (anomalies) settle without touching the order. Bank transfer refunds are recorded as completed at once (money goes back offline).
- A20-14: payments emits no catalogue event itself: `order.paid`, `order.payment_failed`, `order.refunded` come from the orders port inside the same transaction (WP-19's `markPaymentReceived`, `cancelPendingPayment`, `recordRefund` already emit them).
- A20-15: the mock pay page is a plain HTML response from the mock route (dev only), not a React page.
