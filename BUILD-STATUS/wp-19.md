## Assumptions (numbered A19-n, dated 2026-10-20)
- A19-1: Checkout reaches cart, orders, payments, inventory, shipping, discounts, places (states) and marketing (attribution) through `configureCheckout` ports, the Wave 1 `configureX` pattern. checkout's package.json declares no `@ecomkit/orders` (adding it would change the lockfile); orders' `createOrder` matches `CheckoutOrderInput` structurally. Checkout tests therefore use an in-test orders port that takes a real number from `core_sequence` inside the transaction; the real `createOrder` is covered by the orders tests.
- A19-2: checkout's manifest `dependsOn` adds `orders` (plan listed core, cart, auth, customers): a store cannot place an order without it. Optional: payments, shipping, discounts, inventory, places, marketing. Without the payments port `placeOrder` answers `unavailable`.
- A19-3: The guest page `/order/[token]` and its invoice route live in orders (it renders an order). The guest token is an HMAC of the order id under `INTERNAL_SECRET` (purpose `guest-order`); only `sha256(token)` is stored. This makes a replayed place-order able to return the same link. Rotating `INTERNAL_SECRET` invalidates old guest links.
- A19-4: The GST invoice is issued (number + frozen document) by the `order.paid` subscriber (a worker job with standard retries); the PDF is rendered on demand from the frozen document at the invoice routes instead of being stored in media. `pdf_media_id` stays null. Zero-value replacement orders and unpaid orders get no invoice.
- A19-5: COD mode, advance percent and attempt expiry are read from payments through the checkout port (`config()`), not duplicated in checkout settings. Choices: online always; `partial_advance` for deliveries when that mode is on (advance = pct of total rounded up to the rupee); `pay_at_nursery` only with pickup (order starts `confirmed`, stock committed at once, no redirect).
- A19-6: Status machine: `pending_payment -> paid` (system, on payment; also for a partial advance, with `payment_status = partially_paid`), `paid -> confirmed -> packed -> dispatched -> delivered` (staff: orders.write for confirm/pack, orders.dispatch for dispatch/deliver), `cancelled` only while nothing was paid (staff or the sweep), refunds are system moves from `recordRefund`. A paid order is never cancelled (policy: refunds for payment anomalies only).
- A19-7: Reservation `reference` is `checkout:<sessionId>` (the order id does not exist yet when the hold is taken); `orders_order.reservation_id` stores the hold so payment commits it and cancel releases it.
- A19-8: The coupon is re-validated on the checkout page load and at place-order only; address/method re-quotes reuse the stored result so typing an address never burns the discounts module's 10-attempts-per-15-min coupon limit.
- A19-9: Place-order records `order_updates` consent (granted) for the buyer's contact, and `marketing` only when ticked (an explicit tick already records it through `setMarketingConsent`). Consent text carries version `2026-10`.
- A19-10: No shipping module: checkout offers free pickup only. Default method on a fresh checkout is the first available one the shipping module lists.
- A19-11: Manual orders take no stock hold (staff adjust inventory when packing); online manual orders get a payment link from the payments port. Replacement orders do take stock (reserve + commit) when inventory is on.
- A19-12: Order number prefix is the orders setting `numberPrefix` (default `ORD`); the Hasiru store must set it (see requests). Seller state code default is empty, which means intra-state tax until set.
- A19-13: Added columns beyond plan section 3: `orders_order.payment_mode, refunded_paise, advance_paise, totals, reservation_id`; `orders_invoice.taxable_paise, total_paise, document`. CSV export of the orders list is not built (not in this row; DataTable has none yet).
- A19-14: `slotLabel` ("Saturday 24 Oct") exists in both checkout and orders domains (neither may import the other); Wave 5 audit item to move into core.
