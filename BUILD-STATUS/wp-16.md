## Assumptions (A16-n, 2026-10-20)
- A16-1: No cross-module foreign keys (customers -> auth/places, enquiries -> customers/places/media/auth, reviews -> catalog/orders/media/auth). Each module must push and run alone (pick-and-choose); ownership and existence are enforced in queries. Within a module FKs exist (attachments, notes, review media).
- A16-2: Auth user ids are uuids (core `core_audit_log.actor_id` is uuid) and `CustomerViewer.customerId === userId`; `customers_profile.user_id` is the customer key. WP-02 must configure Better Auth to generate uuids.
- A16-3: Lead sources follow the frozen events contract (`wizard | notify_me | enquiry | chat | checkout`); the plan's `exit_intent` is not a source (exit intent sends the cart, it does not create a lead).
- A16-4: `upsertLead` dedupes on phone hash + source + `context.ref` while the lead is open (planting passes `ref: planId`, notify-me `ref: productId`); without a ref every call inserts. The enquiry passes `ref: enquiryId`, so every enquiry is exactly one new lead and one `lead.created`.
- A16-5: Enquiries emit `enquiry.created` (for notifications) besides the lead's `lead.created`; only `lead.created` reaches the ERP. Enquiries never call ops.
- A16-6: Optional cross-module needs go through boot-time ports, not imports: `configureEnquiries({ contacts: contactPort, files })`, `configureReviews({ purchases, images, products })`. Without a port the feature degrades (no lead, no verified flag, no photos, no names) and PII masking fails closed.
- A16-7: Contact hashes are HMAC-SHA256 keyed from `INTERNAL_SECRET` (purpose `contact-hash`), 22 chars base64url; rotating `INTERNAL_SECRET` invalidates stored hashes (re-hash from the plain columns).
- A16-8: Masking: full phone/email only for non-support staff holding `customers.read` and for the customer themself; support, guests and other customers see `+91 98•••••210` / `r•••@example.com`. Without customers wired, enquiries show `••••••` to support.
- A16-9: Consent is append-only; the newest row for any of the subject's identifiers (user id, phone hash, email hash) decides; no row means not granted. Every write also writes a core audit row (`consent.grant` / `consent.revoke`) and emits `consent.changed` in one transaction.
- A16-10: Segment "bulk buyer" = lifetime spend >= Rs 25,000 or a `bulk` tag on the profile (the plan named the segment without a rule). "By district" uses the default address, else the newest. "Wizard lead not converted" excludes leads whose phone belongs to a customer with an order.
- A16-11: `customers_land_profile.purpose` is a free slug (not an enum) so the generic module carries no planting vocabulary; `enquiries_enquiry.customer_type` is text validated by zod (`farmer | business | individual`).
- A16-12: Added columns: `enquiries_enquiry.customer_notes` (the visitor's notes; staff remarks stay in `enquiries_note`), `enquiries_attachment.file_name/content_type/size_bytes/created_at`, `reviews_review.author_name/is_sample/data_source/moderated_by/moderated_at/updated_at`, `reviews_media.position`, `reviews_aggregate.updated_at`.
- A16-13: Enquiry pipeline allows a move to any status (boards are dragged both ways, closed can be reopened). Stale = open and untouched for 3 days (`STALE_AFTER_DAYS`); the dashboard tile turns amber when the newest enquiry is older than 7 days. Constants, not settings.
- A16-14: Enquiry limits: 5 posts per IP hash per hour (plan section 8), up to 5 files of 10 MB (jpeg, png, webp, heic, pdf); a honeypot hit answers "sent" and stores nothing; a too-fast/forged/expired time token answers `retry`. The return path accepts same-site relative paths only.
- A16-15: Reviews: one per customer per product (edit instead), up to 4 photos of 8 MB, 10 submissions per customer per day; an edit returns the review to `pending`. Review photos go through a route handler (`POST /api/reviews`) because the server-action body limit is 1 MB.
- A16-16: Account and admin pages, `/api/enquiry`, `/api/reviews` and the attachment route are declared in the manifests and left to `modules:sync` (no hand-written stubs in `apps/shop/app/api/enquiry/` or the account/admin folders). The only hand-written app files are `/build-farm-with-us` (Hasiru page) and its `copy.ts`.
- A16-17: Hasiru copy for `/build-farm-with-us` lives in `apps/shop/app/(shop)/build-farm-with-us/copy.ts` (this package does not own `messages/en.ts`).
- A16-18: The cross-module test lives in `apps/shop/test/wp-16-enquiry-lead.test.ts` (a new file; the only package that depends on both customers and enquiries is the app). It stubs `server-only` with `vi.doMock` on the resolved path because the shop vitest config has no alias.
- A16-19: Package vitest configs alias `server-only` to an empty test module (`test/server-only.ts`), since `src/server/index.ts` imports it and vitest is not a React server build.
- A16-20: District typeahead on the enquiry form and address form is not wired (places is a separate, optional module); the form takes free-text location and keeps a `districtId` field for when the typeahead island exists.
