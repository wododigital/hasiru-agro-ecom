## Assumptions (numbered A11-n, dated)
- A11-1 (2026-10-20) Nothing hand-written under `apps/shop/app/`: `api/health/{live,ready}` and `(admin)/admin/health/**` come from `modules:sync` via manifest `routes` / `admin.pages` (verified with `planFiles`). The core manifest comment says health routes are hand-written in the app; manifest routes are the same files without a second mechanism. Consequence: disabling monitoring removes `/api/health/*`.
- A11-2 (2026-10-20) `/api/monitoring/vitals` is not built (owned path `api/monitoring/` stays empty). Analytics owns the vitals beacon and `analytics_web_vital`; a second ingest would duplicate it. Web-vitals regressions reach alerting through an analytics `healthChecks` entry (see requests).
- A11-3 (2026-10-20) 404 view: not duplicated. The overview links to the SEO module's 404 log and redirects when `seo` is enabled (seo owns `seo_not_found` and redirect creation).
- A11-4 (2026-10-20) Alert issue lifecycle: one unresolved row per (rule, fingerprint); a new occurrence after resolve opens a new row. "Dedupe window" = a reopened issue stays quiet when the same rule + fingerprint was notified within `dedupe_minutes` (flapping). Continuing conditions seen by scans do not bump counts (`reconcile`); event-driven raises do.
- A11-5 (2026-10-20) Added columns to the plan's `monitoring_alert`: `resolved_at`, `delivery jsonb` (provenance of the last delivery), `created_at`. Digest selection uses `last_at > notified_at`.
- A11-6 (2026-10-20) Channels: rule channels are `whatsapp`, `email`, `webhook`; the bell is the row itself. Defaults: critical WhatsApp + email (repeat 30), high and low email. The webhook is used when no direct channel delivered (or when listed on the rule). Alerts about a channel (`integration.failed` for gmail/whatsapp, `messaging.*`, health checks with ids `notifications.*`) skip that channel.
- A11-7 (2026-10-20) `integration.failed` pages after 3 failures of one provider + operation in 15 minutes (core `integrationCall` emits on every failure, before job retries); resolved when the latest call for it is ok. Job-level "retries exhausted" is covered by the dead-letter scan.
- A11-8 (2026-10-20) Server errors alert per open error issue (level `error`, seen in 7 days) rather than per "new fingerprint" event: resolving or ignoring the issue in Errors resolves the alert; core reopening a resolved issue re-raises it (with flapping protection).
- A11-9 (2026-10-20) Readiness built-ins: database round trip, worker heartbeat (missing or older than 2 min = down), disk (> 10% free and writable for `diskPaths`, default the app folder). Inventory-pull age and image cache are expected as `healthChecks` from erp-sync and media. `/api/health/ready` is memoised 5 s per process and returns ids + statuses only.
- A11-10 (2026-10-20) "Schedule missed by > 2 periods" and DB bloat are not checked (the heartbeat check and the minute tick cover a dead worker; bloat needs pgstattuple). Recorded, not built.
- A11-11 (2026-10-20) Backups are recorded by the backup script inserting a `backup.nightly` row into `monitoring_check_result` (README has the psql line); no backup endpoint.
- A11-12 (2026-10-20) Permissions: Health screens, ack, resolve and error status need `health.read` (no `health.write` exists in CONVENTIONS); rule edits `settings.write`; Retry `jobs.retry`. One sidebar item (Health, order 800) with tabs inside the screens.
- A11-13 (2026-10-20) RDAP lookups go to `https://rdap.org/domain/<apex>` through core `safeFetch` (apex = host without `www.`); unknown expiry is recorded, not alerted. Certificates are read with a TLS connection to port 443.
- A11-14 (2026-10-20) Runtime binding `configureMonitoring({ registry })` (same pattern as core `setAuthProvider`), with injectable `notifications`, `postWebhook` and `statDisk` for tests. Route handlers call `next/server` `connection()` (narrowly tolerated outside a request for unit tests) so they are never prerendered.
- A11-15 (2026-10-20) Observation, not code: this Mac's data volume has about 3% free (`df`: 7.2 GB of 239 GB). The disk check would flag it as down; tests use a fake disk probe plus one real `statfs` test. `next build` needs space; worth clearing before Wave 3.
