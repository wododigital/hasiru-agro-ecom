## Assumptions (A10-n, 2026-10-20)
- A10-1: `notifications_message` has extra columns beyond plan section 3: `category`, `rendered jsonb` (subject, text, WhatsApp params; never the address) for the log and dev outbox. The recipient address is not stored; it travels only in the `notifications.deliver` job data.
- A10-2: `notifications_webhook_event` has extra `kind` and `phone_hash` (hashed sender of inbound messages, used for the 24 h service-window check) and is used for inbound messages and template events too (dedupe keys `wa:<wamid>:<status>`, `wa:in:<wamid>`, `wa:tpl:...`).
- A10-3: `notifications_wa_template_status` adds `paused` and `disabled` (Meta statuses) to the plan's draft/pending/approved/rejected.
- A10-4: Opt-out (STOP) blocks marketing only, on WhatsApp and SMS; order updates and codes still go. No consent event is emitted: `consent.changed` carries customerId/leadId and an inbound STOP only knows a phone. Marketing consent itself stays with customers/flows (A28).
- A10-5: Categories: `otp.*` authentication; `cart.reminder_*`, `review.request`, `stock.back_in_stock`, `lead.follow_up` marketing (every marketing body ends "Reply STOP to stop these messages."); the rest utility.
- A10-6: Every key has email, WhatsApp and SMS text (SMS and log reuse the body; log reuses the email subject). WhatsApp authentication templates are created with Meta's preset text; our body is used for email/SMS only.
- A10-7: Quiet hours default 21:00 to 09:00 IST, marketing only; held messages are delayed (job `startAfter`), not skipped.
- A10-8: Default modes are `mock` for email, WhatsApp and SMS; mock mode needs no credentials (built-in ids), so the dev outbox works out of the box. A production install still in mock mode shows `degraded` on the health check.
- A10-9: Gmail OAuth client comes from env `GMAIL_OAUTH_CLIENT_ID` / `GMAIL_OAUTH_CLIENT_SECRET` (agency client), overridable per store in settings; scope `gmail.send openid email` (openid/email only to learn the mailbox address from the id_token).
- A10-10: Mock mode talks to the in-app mock routes with plain `fetch` on `INTERNAL_BASE_URL`; live/sandbox use `core.safeFetch` with host allowlists.
- A10-11: Admin pages: Message log (Health band, order 820) and Message templates (Settings band, order 920), both `settings.read`; template edits `settings.write`; Connect Gmail `settings.secrets`.
- A10-12: Address hash is HMAC-SHA256 with `derivedSecret('notifications-address')` (phones normalised to E.164 first).
- A10-13: `send` accepts extra options (`orderId`, `flowRunId`, `isTest`) beyond the contract; contract callers are unaffected.
- A10-14: Template overrides may only use the default's variables (+ `store_name`), so callers never have to know about an admin edit.
- A10-15: Route stubs under `apps/shop/app/...` for this row's paths were not hand-written: they are generated by `modules:sync` from the manifest (orchestrator).
