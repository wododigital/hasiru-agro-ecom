## Assumptions (numbered A06-n, dated)
- A06-1 (2026-10-20): `pricing_price` carries `product_id` (not in the plan's column list) so `price.changed { productId }` and the `price:<productId>` tag need no catalog query. No FK to `catalog_variant`: catalog does not exist in this wave and modules never reach into another module's tables.
- A06-2 (2026-10-20): GST rate and a product's variant list come from catalog through `configurePricing({ gstRates, variantsOf })`, called by the app at boot. Reads throw a clear "pricing is not configured" error until wired. A product missing from `gstRates` quotes at 0% (catalog's data gap).
- A06-3 (2026-10-20): cross-line summation default groups by variant (prototype C2.7: package + extra lines of the same plant). Wider pooling (per product, cross-plant bulk, an open client question) is the `groupKey` option, not a setting.
- A06-4 (2026-10-20): a tier whose price is not below list is ignored (never raises a price); admin validation requires tiers to get strictly cheaper as `min_qty` rises, `min_qty >= 2`, max 10 tiers, compare-at above price.
- A06-5 (2026-10-20): saving identical prices writes no audit row and emits nothing. Price saves through the admin need `pricing.write`; `getAdminPricing` (offline + cost) needs `products.read`.
- A06-6 (2026-10-20): among automatic promos, all stackable ones apply plus only the best non-stackable one (largest amount, then priority, then id). The coupon-versus-promo best-of stays in `core.computeTotals` (A00b-7), not duplicated here.
- A06-7 (2026-10-20): percent values are whole percents (1..100); fixed values are paise (admin types rupees). Percent amount is rounded once on the target subtotal, then allocated to lines by value (largest remainder). `min_qty` and `min_subtotal_paise` measure the targeted lines at tier prices.
- A06-8 (2026-10-20): windows are `timestamptz`, start inclusive, end exclusive; the admin enters India time in `datetime-local` fields (`istLocalToDate`/`toIstLocal`).
- A06-9 (2026-10-20): coupon brute-force limit = 10 attempts per subject per 15 minutes (`coupon-apply:<subject>`, counted before any lookup); the caller picks the subject (cart id, phone hash or IP hash). Unknown, expired, paused and other-customer codes all answer `invalid`.
- A06-10 (2026-10-20): per-customer limits count by phone hash or customer id; a rule with a per-customer limit refuses redemption without either. Single-use personal codes (`single_use_phone_hash`) work for that phone once (for flows' follow-up offers via `createSingleUseCode`).
- A06-11 (2026-10-20): redemptions are deleted on `order.cancelled` and `order.payment_failed` so usage limits count only real orders. `redeem` re-checks the window at place-order time (`not_live`).
- A06-12 (2026-10-20): discount status enum `draft|active|paused|archived` (plan said only `status`). Discounts admin uses permission `marketing.write` (no discount-specific permission in the frozen list).
- A06-13 (2026-10-20): discount targets are entered as ids (one per line) until a catalog picker exists; the cart supplies `collectionIds`/`tagIds` per line in the same id space.
- A06-14 (2026-10-20): `apps/shop/app/(admin)/admin/discounts/` is left empty: its three page stubs come from the manifest's `admin.pages` via `modules:sync` (orchestrator). No hand-written files there.
- A06-15 (2026-10-20): `server/index.ts` imports `server-only`; the manifest's lazy imports point at `server/pricing.ts`, `server/events.ts` and `admin/PricingTab.tsx` directly so the worker (plain Node) can load providers and event handlers (same reason as A00b-1).
