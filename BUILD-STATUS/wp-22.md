## Assumptions (A22-n, 2026-10-20)
- A22-1: Cart, orders, discounts, catalog and the lead read are reached through boot-time ports (`configureFlows`), the A16-6 pattern; they are `optional` in the manifest. An unbound port makes the flows that need it record a `subject_missing` run and send nothing.
- A22-2: The plan's quiet hours for abandoned cart ("9 to 11 and 18:30 to 21:00 IST") are commute windows a scheduled message is moved out of (to the window end), per cro-ux section 4. They are per-flow settings (list of `HH:MM-HH:MM`, may wrap midnight). The night hold for marketing (21:00 to 09:00) stays in notifications (A10-7) and applies on top.
- A22-3: Delays count from the run start (abandonment, delivery, lead), not from the previous message.
- A22-4: `flows_run` columns beyond the plan: `contact_hash` (core `hashContact` of phone, else email; the plan's `phone_hash`), `position`, `context jsonb` (ids, stage, slot date, code, `restoredAt`; no personal data), `messages`, `is_test`, `updated_at`. `flows_flow` adds `updated_by`, `updated_at`. No contact is stored by flows; it is read fresh at each step.
- A22-5: Steps are four rows per settings step (wait, stop_if, send_whatsapp, send_email), each with `enabled`; a settings save updates the rows in place so running runs keep their position and continue with the new settings.
- A22-6: Channel per step is WhatsApp, email or both; a channel without an address for that contact is skipped (recorded on the run step), so "max 3 messages" means at most 3 per channel.
- A22-7: One sequence per 7 days counts runs of the same flow for the same contact hash that were not stopped at start (`no_contact`, `no_consent`, `frequency_cap`, `subject_missing`); starts are serialised per contact with an advisory lock.
- A22-8: Marketing consent is checked at start (`no_consent`) and before every send (`unsubscribed`). Back in stock needs no separate consent check (the notify-me request with its checkbox is the consent, A07-10). Review request and planner follow-up are marketing templates (A10-5), so they need recorded marketing consent; a planner lead without it gets no follow-up.
- A22-9: Stop on reply = any inbound WhatsApp from the contact after the run started (notifications `lastInboundAt`); a STOP reply is an inbound message, so it stops too.
- A22-10: Order updates are one flow with four stages; `order.paid` and `order.confirmed` both mean "confirmed" (first wins, once per order). Stage messages are utility and need no consent. The flows module owns these customer messages; orders should not send them itself (request below).
- A22-11: The single-use code is created once per run on the 72 h step (discounts `createSingleUseCode`, bound to the phone) and applied by the restore link. `cart.reminder_3` has no `{{code}}` variable, so the code is not printed in the message (request below).
- A22-12: Back in stock is delivered through `backInStockSender`, a `NotificationSender` the host gives inventory (`setNotificationsProvider`); inventory keeps its claim-then-send. It is always sent at once (a delay is rejected: the contact is not stored). Pausing the flow means requests delivered while paused are marked notified by inventory and get no message.
- A22-13: `/r/[token]` is a route handler (it must set the cart cookie), so `modules:sync` writes it to `app/r/[token]/route.ts`, not under the row's `app/(shop)/r/`. The token is `<runId>.<32 hex HMAC>` (purpose `flows-restore`); `/r/` is already case-exempt in `proxy.ts`. Invalid tokens also 303 to `/cart` (no oracle).
- A22-14: Flow rows are created lazily with defaults (`ensureFlows` on first read), so no seed hook is needed.
- A22-15: Admin pages: Automations under Marketing (order 410, `marketing.write`), Abandoned checkouts under Orders (order 140, `orders.read`). Test run sends to a staff phone and/or email with example values, flagged `is_test`, recorded as a completed test run.
- A22-16: Route stubs under `apps/shop/app/...` are not committed: they come from `modules:sync` (orchestrator). The build check above added and then reverted them.
