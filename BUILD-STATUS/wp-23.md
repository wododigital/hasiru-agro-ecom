## Assumptions (A23-n, 2026-10-20)
- A23-1: Built-in vendors (GA4, Meta Pixel + CAPI, Google Ads) are configured in module settings; `marketing_tag` holds admin-added custom tags (its `vendor` column labels them). An empty id switches a vendor off.
- A23-2: An anonymous visitor's banner choice lives only in the first-party `ek_consent` cookie; `customers_consent` rows are written when the visitor is a signed-in customer (subject = user id + phone + email). The customers subject schema requires a user, phone or email, so the plan's "keyed by visitor cookie hash" needs a customers change (request below).
- A23-3: Banner "Analytics" = purpose `analytics_identity`; "Advertising" = purpose `marketing`. A repeated choice only records the purposes that changed (compared with the cookie).
- A23-4: Server conversions honour the consent snapshot stored with the order (`marketing_attribution.consent_analytics/consent_marketing`): GA4 needs analytics, CAPI needs advertising. No attribution row = no consent = `skipped_consent` (fail closed).
- A23-5: `marketing_conversion_event.event_id` is text, unique per `(destination, event_id)` (plan: uuid unique): `purchase.<orderId>` is shared with the browser pixel for Meta dedup; refunds use `refund.<refundId>`.
- A23-6: `marketing_attribution` adds `ga_client_id`, `consent_analytics`, `consent_marketing`, `user_agent`, `created_at`. No raw client IP is stored, so CAPI events carry no `client_ip_address` (hashed email/phone, fbp/fbc and user agent instead).
- A23-7: GA4 `purchase`/`refund` are server-only (MP); the browser sends no GA4 purchase. The Ads purchase conversion is browser-side (`transaction_id` = order number; optional enhanced conversions with advertising consent); no server Ads upload. Meta has no refund event.
- A23-8: Orders are reached through a port, `configureMarketing({ orders: { forConversion(orderId) } })` returning a `ConversionOrder` (in `domain/conversions.ts`), because orders ships in this wave. Without the port, conversions are skipped with a log line.
- A23-9: Tests route vendor HTTP to the in-package mock handlers in process (`configureMarketing({ http })`), not over TCP; the handlers are the same code the app mounts.
- A23-10: `cspSources()` returns `{ script, connect, img, frame }`, memoised 60 s per process (no query per request), empty on a failed read. Custom tag hosts must be `https://host[:port]` (optionally `*.`), anything else is dropped.
- A23-11: Attribution cookies (`ek_ft` first touch, `ek_lt` last touch, `ek_click` click ids; 90 days) are written only after advertising consent; the landing URL's data is held in memory until then. `gbraid`/`wbraid` fall back into the `gclid` column.
- A23-12: `TagScripts` reads `publicTagConfig()` (`'use cache'`, tag `settings:marketing`), so the storefront shell stays static; tag saves and settings saves expire it.
- A23-13: Settings text fields are `z.coerce.string()` with a regex that accepts empty: core_settings is jsonb and drizzle's jsonb reader JSON-parses stored strings a second time, so digits-only ids come back as numbers (request to core below). Coerce (not preprocess or unions) keeps them plain text inputs in admin-shell's settings form.
- A23-14: `@ecomkit/marketing` gained a `./client` export (`src/ui/browser.ts`: `marketingTrack`, `openConsentSettings`) so client code never imports the server-bound `ui` index.
- A23-15: `feeds_file` table added (pk destination; body, content type, etag, items, generated_at): the generated file lives in Postgres so web and worker share it without a disk path setting.
- A23-16: One item per variant: `id` = product sku + variant suffix; `item_group_id` = product sku for multi-variant products, whose link carries `?variant=<suffix>`.
- A23-17: Google image = 800 px WebP derivative (largest below 800 for small masters); Meta image = the share JPEG. URLs assume the media warm job generated the derivatives.
- A23-18: Feed price = online list price for qty 1, GST-inclusive; with a real compare-at, `price` = compare-at and `sale_price` = list. Bulk tiers are not in feeds.
- A23-19: Feeds include only visible (`active`, not hidden, not deleted), indexable (`noindex = false`) products. Variants without a price or image are rejected with a reason (`feeds_item_state.last_error`, admin page), never shipped at Rs 0. Out-of-stock items stay in as `out_of_stock` unless `includeOutOfStock` is off.
- A23-20: Availability = catalog `offerAvailability(deriveAvailability(...))`; `preorder` gets `availability_date` = today + ready-in days (30 when unknown).
- A23-21: Debounce = queue policy `stately` + `startAfter` = now + `debounceSec` (default 120): the first change queues one rebuild, later changes inside the window fold into it. Daily forced rebuild at 03:15 IST.
- A23-22: Feed URLs: missing or wrong token 403, destination off 404, first fetch builds the file when none exists, `ETag` + 304, `X-Robots-Tag: noindex`. "Generate new feed token" replaces the token (old URLs stop working).
- A23-23: Shipping for Google is configured at account level in Merchant Center (not in the feed).
- A23-24: Brand and Google categories are settings, empty by default (brand-neutral package). Hasiru values to enter: brand "Hasiru Agro", plant category "Home & Garden > Plants" (id to verify, research open item 5).
- A23-25: Feed rows come from catalog `listProducts` + `getProductBySlug` per product (8 at a time) because catalog has no bulk variant export; fine for under 500 products in a worker job.
